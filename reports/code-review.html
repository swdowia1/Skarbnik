Potwierdzone błędy i ryzyka

Wysoki Logowanie używa przewidywalnego hasła, a kompilacja DEBUG pomija jego sprawdzenie

Kategoria: bezpieczeństwo / uwierzytelnianie
Lokalizacja: Skarbnik/Pages/Login.cshtml.cs:38–53

Obecne zachowanie: hasło jest wyliczane z bieżącej daty według stałego wzorca; w bloku #if DEBUG nie ma weryfikacji hasła i żądanie przechodzi do utworzenia cookie administratora.

Uzasadnienie: wzorzec oparty na publicznie znanej dacie jest odgadywalny. Każda kompilacja DEBUG pozwala uzyskać sesję administratora bez poprawnego hasła. Wartość hasła nie jest ujawniana w raporcie.

Minimalna poprawka: weryfikować sekret przechowywany poza kodem i jednakowo wymagać go we wszystkich konfiguracjach; usunąć ścieżkę pomijającą kontrolę.

Wysoki Eksport danych uczniów i płatności nie wymaga logowania

Kategoria: bezpieczeństwo / poufność danych
Lokalizacja: Skarbnik/Pages/Index.cshtml.cs:19

Obecne zachowanie: handler OnGetTestExcelAsync pobiera uczniów, wydatki i przypisania oraz zwraca plik Excel. Klasa IndexModel nie ma [Authorize], a konfiguracja Razor Pages w Program.cs nie ustawia globalnej konwencji autoryzacji. Link do eksportu jest renderowany na stronie głównej.

Uzasadnienie: handler Razor jest dostępny bez jawnego wymogu uwierzytelnienia, więc anonimowy klient może pobrać zestaw danych obejmujący nazwiska i statusy wpłat.

Minimalna poprawka: wymagać autoryzacji na handlerze albo całej stronie eksportu i ukrywać link dla niezalogowanych użytkowników.

Wysoki Handler przypisywania płatności pozwala anonimowo zmieniać dane

Kategoria: bezpieczeństwo / autoryzacja operacji modyfikujących
Lokalizacja: Skarbnik/Pages/Przypisz.cshtml.cs:33–43

Obecne zachowanie: OnPostAsync nie sprawdza użytkownika ani nie ma [Authorize]. Przyjmuje z formularza identyfikatory oraz czyZaplacono, a następnie wywołuje zapis przypisania. Strona zawiera formularz pozwalający przekazać status opłacenia.

Uzasadnienie: w Program.cs nie skonfigurowano globalnego wymogu logowania dla Razor Pages. Sama widoczność przycisków nie zabezpiecza bezpośredniego żądania POST.

Minimalna poprawka: wymagać autoryzacji po stronie serwera na stronie lub handlerze oraz nie traktować statusu płatności z formularza jako uprawnienia użytkownika.

Wysoki Dwa handlery szczegółów wydatku modyfikują dane bez kontroli logowania

Kategoria: bezpieczeństwo / autoryzacja operacji modyfikujących
Lokalizacja: Skarbnik/Pages/Szczegoly.cshtml.cs:18–24 oraz :38–45

Obecne zachowanie: OnPostZaplaconoAsync oznacza przypisanie jako opłacone, a OnPostUsunAsync usuwa je. Żaden z tych handlerów nie wymaga uwierzytelnienia. W tym samym modelu OnPostNiezaplaconeAsync wykonuje jawny test User.IsLoggedIn(), co potwierdza, że sama strona nie jest globalnie chroniona.

Uzasadnienie: anonimowe żądania POST mogą zmieniać status wpłaty i usuwać przypisania pomimo ukrycia formularzy w widoku.

Minimalna poprawka: zastosować spójną autoryzację po stronie serwera do wszystkich handlerów modyfikujących.

Błędy jakościowe i pozostałe rekomendacje

Średni Handler przypisania ignoruje wynik operacji serwisu

Lokalizacja: Skarbnik/Pages/Przypisz.cshtml.cs:41–43. PrzypiszWydatekAsync zwraca false dla nieistniejących lub już przypisanych rekordów, ale handler ignoruje wynik i zawsze przekierowuje jak po sukcesie. Użytkownik nie dostaje informacji, że zapis nie nastąpił. Minimalna poprawka: sprawdzić wynik i przekazać błąd lub odpowiedni wynik HTTP.

Niska Niezużyty hasher i nadmiarowe importy w modelu logowania

Lokalizacja: Skarbnik/Pages/Login.cshtml.cs:4–5, 16–24. PasswordHasher jest tworzony, ale nie jest używany; import Microsoft.Extensions.Options nie jest używany i można go usunąć przy porządkowaniu. Import Skarbnik.Extensions jest używany przez ToWarsawTime(). Usunięcie nieużywanego pola nie zastępuje koniecznej poprawy uwierzytelniania.

Niska Kształtowanie loginu jako klasyczne Razor Pages jest nierówne

W projekcie tylko `DodajWydatekModel` i `EdytujUczniaModel` mają klasowe [Authorize]; API ma atrybut na kontrolerze, a pozostałe operacje zależą od ręcznych kontroli albo ich nie mają. Zalecenie dotyczy ujednolicenia zasad autoryzacji; konkretne braki opisano jako potwierdzone błędy powyżej.

Brakujące lub zalecane testy

Projekt zawiera jeden zestaw UczenServiceTests z 14 testami faktowymi. Testy używają izolowanego SQLite in-memory. Nie znaleziono testów integracyjnych dla Razor Pages, API ani logowania.

  • Dodaj testy autoryzacji HTTP dla eksportu Excel oraz mutujących handlerów Razor: użytkownik anonimowy powinien otrzymać przekierowanie/odmowę, a uwierzytelniony poprawny wynik.
  • Dodaj test logowania w konfiguracji DEBUG i Release: błędne/nieobecne hasło nie może utworzyć tożsamości administratora.
  • Dodaj test handlera przypisania, który potwierdzi obsługę wyniku false (duplikat) i brak fałszywego sukcesu.
  • Dodaj test dla DodajWydatekDlaWszystkichAsync, weryfikujący powstanie wydatku i nieopłaconych przypisań dla wszystkich uczniów.

To rekomendacje; testy nie zostały dodane ani uruchomione.
